# 2026.277.1356 — fix(k3s): align the pinned k3s to v1.37.0+k3s1 (Kubernetes v1.37.0 = kind's node image) — root-cause fix for the containerDisk VMI crash

## Summary

The pinned k3s was **`v1.31.11+k3s1`** — Kubernetes **v1.31**, where the upstream Kubernetes `ImageVolume` volume source is **alpha/off**. KubeVirt's own `ImageVolume` feature gate is **Beta** (enabled by default since v1.7.0), so on a v1.31 cluster a containerDisk VMI's ImageVolume init container cannot exec its helper binary and **crash-loops**:

```
exec: "/container-disk-binary/usr/bin/container-disk":
stat /container-disk-binary/usr/bin/container-disk: no such file or directory
```

The correct fix is to run a Kubernetes where the `ImageVolume` source is enabled — **not** to force-disable KubeVirt's capability. Bump the pinned k3s to **`v1.37.0+k3s1`** (Kubernetes **v1.37.0**) — deliberately the EXACT Kubernetes version **kind** already deploys (`kindest/node:v1.37.0`, kind's current default node image), so both substrates run K8s **v1.37.0**. (k3s also publishes `v1.37.1+k3s1`, but `v1.37.0+k3s1` matches kind's node image exactly; kind is already on the latest node image, so no kind change is needed — this makes k3s MATCH it.)
