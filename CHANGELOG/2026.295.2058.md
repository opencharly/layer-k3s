## Summary

Add the `k3s-shared-containerd` layer (CONTAINERD-IMAGES.md §1.7) to `opencharly/layer-k3s`, composing the existing verified-checksum `k3s` candy.

- `/etc/rancher/k3s/config.yaml` carries `container-runtime-endpoint: unix:///run/containerd/containerd.sock`, so k3s never starts its embedded containerd (K3S.md §1, §2.2).
- `/etc/containerd/conf.d/50-k3s-cni.toml` is a **partial** config with only the two k3s-specific CNI keys — `bin_dirs = ["/var/lib/rancher/k3s/data/current/bin"]` and `conf_dir = "/var/lib/rancher/k3s/agent/etc/cni/net.d"` (K3S.md §2.1). The shared daemon's own version-4 config, root/state dirs, and CRI handlers stay owned by the containerd-host image.
- `/var/lib/rancher/k3s/server/manifests/krun-runtimeclass.yaml` and `nvidia-runtimeclass.yaml` declare `node.k8s.io/v1` RuntimeClasses (`handler: krun`, `handler: nvidia`). k3s auto-applies that directory, so no imperative `kubectl apply` (K3S.md §4).
- `files/k3s-runtime-handler-guard.sh` (copied to `/usr/local/bin/k3s-runtime-handler-guard`) fingerprints the merged containerd CRI runtime map (`containerd config dump`, which includes `conf.d`) and encodes the restart-after-handler-change rule (K3S.md §2.3 step 3). It is a no-op where the shared daemon's socket does not exist (an image build, or a host that has not started containerd). Where the socket exists it records the baseline — the install step runs before k3s starts, so that is the set the server latches — and on later applications it restarts k3s only when the fingerprint changed while k3s was running. A first application to an already-running k3s restarts once, because that k3s latched a set older than this layer.
- `test/k3s-runtime-handler-guard-test.sh` covers all seven guard branches (socket absent; baseline; unchanged; changed-while-running; changed-while-inactive; first-active; unchanged-after-change).

Also added: deterministic `check:` steps for every installed artifact, the `k3s-shared-containerd-app` local template, the `check-k3s-shared-containerd` bed (absence → perform → presence → guard-idempotent), and README / `.agents/skills/k3s/SKILL.md` / `AGENTS.md` updates. The README's stale pinned version (`v1.31.11+k3s1`) is corrected to the actual pin (`v1.37.0+k3s1`).

No Go in this repo, so `spec`/`sdk` are not bumped.

The `nerdctl -n k8s.io ps` line is the discriminating proof: an embedded containerd would hold those containers on its own socket, leaving the shared socket's `k8s.io` namespace empty. This run is on the final tree (`b336ab4`).

**Daemon safety.** The host's system socket was recorded before and after: `inode=1653 mtime=1790272925` both times. The private daemon listened only at `/tmp/k3s-shared-proof/containerd.sock{,.ttrpc}`; after teardown `ss -lx` showed zero `/tmp/k3s-shared-proof` sockets and no test processes.

One incident, disclosed with its RCA: the first prefetch daemon used `containerd config default`, whose `[plugins.'io.containerd.server.v1.ttrpc'] address` defaults to `/run/containerd/containerd.sock.ttrpc`; `--address` overrides only the gRPC address, so that daemon briefly bound the host's ttrpc sibling path. The missed control was checking only `--address`, not every derived listen address. The root fix was to set the ttrpc address explicitly to a private path **and** run the daemon under a private mount namespace with a tmpfs over `/run/containerd`; every later run, including the proof above, had both addresses under `/tmp`. The host's gRPC socket stayed healthy throughout (`ctr version` → server v2.3.5), and every host-side artifact the test created (`/etc/rancher`, `/var/lib/rancher`, `/var/lib/cni`, `/run/{netns,flannel,k3s}`, the transient `/sys/fs/cgroup/{k3s,kubepods}`) was removed.

**Not run: the bed itself.** `check-k3s-shared-containerd` is a `host: local` bed whose venue must be a disposable containerd-host image; running it on this non-disposable host would write `/etc`, install k3s, and start a control plane against the host's system socket. The bed is authored with the absence → perform → presence → guard-idempotent shape and the presence step carries `eventually: 120s` for the RuntimeClass/addon settle. The live proof above exercised the same mechanism on a private socket instead; the config's endpoint is the one line adapted for that isolation.
